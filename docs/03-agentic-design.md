# طراحی عامل‌محور زیر نظارت، بدون اغراق درباره امکانات

## سه نوع فعالیت

**الف) علمی:** خواندن مقاله، داوری دلالت، استنتاج، روش‌شناسی و نگارش. به Chat متخصص یا پژوهشگر واگذار شود.

**ب) اداری/ماشینی:** نام‌گذاری، شمارش، تطبیق شناسه، تشخیص فایل مفقود، ثبت نسخه، راه‌اندازی تست و Status Board. مناسب اتوماسیون قانون‌محور.

**ج) پرخطر یا برگشت‌ناپذیر:** اشتراک عمومی، حذف داده، تغییر شواهد تأییدشده، ادغام نهایی، مجوز اخلاقی. نیازمند تأیید انسانی صریح.

## معماری پیشنهادی

`Researcher → Coordinator (Work یا ابزار دیگر) → Job Cards → Specialist Chats → Reviewer Chats → Quality Gates → Canonical Artifacts → Researcher Approval`

Coordinator قبل از ارسال باید سطح اجرا را تأیید کند: اگر وظیفه در Chat عادی مقرر شده است، انجام همان کار در Work جایگزین مجاز نیست. متن پرامپت «Chat» تضمین نمی‌کند محیط مقصد واقعاً Chat است. توان ساخت Chat، خواندن پاسخ، ذخیره فایل، ادامه و کار هم‌زمان **برای هر حساب و ابزار باید جداگانه آزمایش شود**.

## شروط ادعای «خودکار»

1. اجرا واقعاً با دسترسی معتبر انجام شده باشد؛ نه فقط پرامپتی که خواسته انجام شود.
2. ورودی، خروجی و لاگ قابل‌وارسی باشند.
3. خطا/قطع ارتباط، اقدام غیرمجاز یا تغییر سطح اجرا باعث BLOCKED شود.
4. نتیجه بدون تأیید لازم به ACCEPTED/Published تبدیل نشود.
5. تعداد عامل‌ها متناسب با کار و محدودیت واقعی باشد؛ یک عدد ثابت، قانون کلی نیست.

## دروازه‌های کیفیت

- ساختاری: وجود فایل، کلیدها، قالب، تعداد و شناسه‌ها → آزمون ماشینی
- محتوایی: نسبت ادعا–شاهد، سوگیری، روش‌شناسی → داور متخصص
- حکمرانی: انتشار، حقوق، داده حساس، تغییر مبنا → پژوهشگر

**توجه:** اسکریپت‌های این مخزن فقط دروازهٔ ساختاری و شبیه‌سازی حالت را می‌آزمایند؛ Work/Chat را اجرا نمی‌کنند.
